# ADR-008: Key Rotation and Passphrase Change Strategy (Three-Tier Hierarchy)

## Status
Accepted

## Context
Padlock must support secure passphrase changes without:
- Re-encrypting the entire vault (slow, error-prone for large vaults)
- Exposing all entry data during the operation
- Leaving old passphrases able to decrypt data
- Requiring downtime or manual intervention

The solution must also support future key rotation scenarios:
- Cryptographic algorithm upgrades (e.g., XChaCha20 → future quantum-resistant cipher)
- Compromised key recovery
- Compliance-driven key rotation policies

## Decision
Implement a **three-tier key hierarchy** with cryptographic indirection:

```
Passphrase (user input, changeable)
     ↓ Argon2id (19 MiB, 2 iterations)
Passphrase Derived Key (PDK, 32 bytes, ephemeral)
     ↓ XChaCha20-Poly1305 decrypt
Key Encryption Key (KEK, 32 bytes, stored encrypted in vault)
     ↓ HKDF derive per-entry keys
Data Encryption Keys (DEKs, 32 bytes each, ephemeral)
     ↓ XChaCha20-Poly1305 encrypt/decrypt
Entry Data (plaintext during use, encrypted at rest)
```

**Key Roles:**

1. **Passphrase Derived Key (PDK)**
   - Derived: `PDK = Argon2id(passphrase, salt)`
   - Purpose: Decrypt KEK blob in vault header
   - Lifetime: Ephemeral (never stored, recomputed from passphrase)
   - Rotation trigger: User changes passphrase

2. **Key Encryption Key (KEK)**
   - Stored: Encrypted in vault header with PDK
   - Purpose: Derive all entry DEKs
   - Lifetime: Persisted in vault, rotates on passphrase change
   - Rotation cost: O(1) — only re-encrypt 32-byte KEK, not entries

3. **Data Encryption Keys (DEKs)**
   - Derived: `DEK = HKDF-SHA256(KEK, "entry-dek" || entry_id)`
   - Purpose: Encrypt individual entry data
   - Lifetime: Ephemeral (derived on-demand, never stored)
   - Count: One per entry (deterministic derivation from entry UUID)

## Rationale

### Why Three Tiers
1. **Passphrase change = O(1) operation**
   - Only re-encrypt KEK blob (48 bytes: nonce + ciphertext + tag)
   - No need to re-encrypt entry data (could be megabytes)
   - Sub-second operation even with 10,000 entries

2. **Cryptographic separation**
   - Compromise of one entry DEK doesn't affect other entries
   - KEK compromise requires vault file + passphrase (both required)
   - Per-entry DEKs enable future entry-level permissions

3. **Key derivation = deterministic DEKs**
   - No need to store per-entry keys
   - No risk of losing encryption keys
   - Entry UUID → DEK mapping is deterministic

### Passphrase Change Flow
```rust
// 1. User provides old_passphrase and new_passphrase
let old_pdk = Argon2id::derive(old_passphrase, vault.salt);
let kek = decrypt_kek(vault.encrypted_kek, old_pdk)?; // Verify old passphrase

// 2. Generate new PDK from new passphrase
let new_pdk = Argon2id::derive(new_passphrase, new_salt);

// 3. Re-encrypt KEK with new PDK (O(1) operation)
let new_encrypted_kek = encrypt_kek(kek, new_pdk)?;

// 4. Update vault header atomically
vault.salt = new_salt;
vault.encrypted_kek = new_encrypted_kek;
atomic_write_vault(vault)?;

// Entry data unchanged, DEKs still derived from same KEK
```

**Time complexity:** O(1) — independent of entry count
**Cryptographic operations:** 2× Argon2id (old + new) + 2× XChaCha20-Poly1305 (decrypt + encrypt KEK)

### KEK Rotation (Future: Cryptographic Upgrade)
If Padlock needs to upgrade from XChaCha20 to a post-quantum cipher:

```rust
// 1. Generate new KEK with new algorithm
let new_kek = generate_kek_v2(quantum_resistant_rng)?;

// 2. Re-encrypt ALL entries with DEKs derived from new KEK
for entry in vault.entries {
    let old_dek = derive_dek(old_kek, entry.id);
    let plaintext = decrypt(entry.ciphertext, old_dek)?;

    let new_dek = derive_dek_v2(new_kek, entry.id);
    entry.ciphertext = encrypt_v2(plaintext, new_dek)?;
}

// 3. Encrypt new KEK with PDK
vault.encrypted_kek = encrypt_kek(new_kek, pdk)?;
vault.version = "2.0"; // Mark vault as upgraded
```

**Time complexity:** O(n) — must re-encrypt all entries
**Trigger:** Manual admin operation or policy-driven rotation

### Security Properties
1. **Forward secrecy**: Changing passphrase makes old PDK unable to decrypt new KEK
2. **Entry isolation**: Each entry has unique DEK (can't use one entry's DEK to decrypt another)
3. **Deterministic derivation**: Entry DEKs reproducible from KEK + entry ID
4. **No key storage**: Only KEK stored (encrypted), PDK and DEKs ephemeral

## Consequences

**Positive:**
- **Fast passphrase change**: Sub-second even with large vaults
- **Simple implementation**: No key database, no key rotation scheduler
- **Flexible**: Supports both passphrase change (O(1)) and cryptographic upgrade (O(n))
- **Secure**: Cryptographic separation between passphrase and entry data

**Negative:**
- **KEK compromise = total loss**: If KEK leaked, all entries compromised (mitigated by storing KEK encrypted)
- **No per-entry passphrase**: All entries share same KEK (acceptable for single-user vault)
- **KEK rotation costly**: Cryptographic upgrade requires re-encrypting all entries

**Mitigation:**
- KEK stored encrypted in vault (requires both vault file + passphrase)
- KEK in memory protected with `mlock` (prevent swapping to disk)
- Future: Per-entry permissions via key wrapping (Phase 11+)

## Alternatives Considered

1. **Single-tier (passphrase directly encrypts entries)**
   - **Rejected**: Passphrase change requires re-encrypting entire vault (O(n) operation)

2. **Two-tier (PDK → DEKs, no KEK)**
   - **Rejected**: Passphrase change still requires re-encrypting all entries

3. **Per-entry passphrases**
   - **Rejected**: UX nightmare, no benefit for single-user vault

4. **Key wrapping with KEK + per-entry random DEKs (stored encrypted)**
   - **Rejected**: Must store N encrypted DEKs (more complex, no security benefit over HKDF derivation)

5. **Hardware Security Module (HSM) for KEK storage**
   - **Not rejected, future enhancement**: Phase 9 platform integration can use Secure Enclave/TPM for KEK
