# ADR-006: Entry Types and Serialization (7 Types, MessagePack)

## Status
Accepted

## Context
Padlock stores diverse credential types (passwords, API keys, SSH keys, certificates, TOTP seeds, etc.). The type system must:
- Provide type safety (prevent storing SSH key in password field)
- Support rich metadata (creation time, tags, custom fields)
- Enable efficient serialization (compact storage)
- Allow schema evolution (add new entry types without breaking existing vaults)
- Facilitate type-specific operations (e.g., TOTP code generation)

## Decision
Define **7 strongly-typed entry variants** using a Rust enum, serialized to MessagePack:

```rust
#[derive(Serialize, Deserialize, Zeroize, ZeroizeOnDrop)]
pub enum Entry {
    Password(PasswordEntry),
    SSHKey(SSHKeyEntry),
    APIKey(APIKeyEntry),
    TOTP(TOTPEntry),
    Certificate(CertificateEntry),
    Note(NoteEntry),
    Generic(GenericEntry),
}
```

**Common Metadata** (all entry types):
```rust
pub struct EntryMetadata {
    pub id: Uuid,
    pub name: String,
    pub tags: Vec<String>,
    pub created: DateTime<Utc>,
    pub modified: DateTime<Utc>,
    pub accessed: Option<DateTime<Utc>>,
    pub favorite: bool,
}
```

**Entry Type Details:**

1. **PasswordEntry**: `{username, password, url, notes}`
2. **SSHKeyEntry**: `{private_key, public_key, key_type (RSA/Ed25519/ECDSA), passphrase?}`
3. **APIKeyEntry**: `{key, secret?, endpoint, scopes[]}`
4. **TOTPEntry**: `{secret, algorithm (SHA1/SHA256), digits (6/8), period (30s)}`
5. **CertificateEntry**: `{cert_chain, private_key, format (PEM/DER), expiry}`
6. **NoteEntry**: `{markdown_text}`
7. **GenericEntry**: `{key_value_pairs: HashMap<String, SecretBuf>}`

**Serialization:** MessagePack via `rmp-serde`

## Rationale

### Why Enum-Based Entry Types
1. **Type safety**: Compiler prevents invalid field access (can't get `username` from `SSHKeyEntry`)
2. **Exhaustive matching**: Pattern matching forces handling all entry types
3. **Rich types**: Each variant has specific fields, no stringly-typed data
4. **Schema validation**: Impossible to create malformed entries

### Why These 7 Types
- **Password**: Core use case (web logins, database passwords)
- **SSHKey**: Essential for Git, server access
- **APIKey**: Growing use case (cloud services, CI/CD)
- **TOTP**: Two-factor auth codes (Google Authenticator compatible)
- **Certificate**: TLS certs, client certificates
- **Note**: Encrypted notes, recovery codes
- **Generic**: Escape hatch for custom data (key-value pairs)

### Why MessagePack Serialization
1. **Compact**: 20-40% smaller than JSON, comparable to Protobuf
2. **Schema evolution**: Self-describing format supports adding fields
3. **Rich types**: Native support for bytes, maps, arrays, timestamps
4. **Rust integration**: Excellent `serde` support via `rmp-serde`
5. **Human-debuggable**: Can inspect with CLI tools (`msgpack-tools`)
6. **No compilation**: Unlike Protobuf, no schema compilation step

### Entry Encryption Model
- Each entry encrypted with a unique **Data Encryption Key (DEK)**
- DEK derived from KEK via HKDF: `DEK = HKDF(KEK, entry_id)`
- Serialization flow: `Entry → MessagePack → XChaCha20-Poly1305 → vault file`
- See ADR-008 for full key hierarchy

### Schema Evolution Strategy
**Adding new entry type:**
```rust
// v0.2 adds DatabaseEntry
pub enum Entry {
    Password(PasswordEntry),
    // ... existing 7 types
    Database(DatabaseEntry), // new in v0.2
}
```
- Old clients: Deserialize unknown variant as `Generic` (graceful degradation)
- New clients: Full support for new type
- Vault file version incremented (minor bump: 0.1 → 0.2)

**Adding field to existing type:**
```rust
pub struct PasswordEntry {
    pub username: String,
    pub password: SecretBuf,
    pub url: Option<String>,
    pub notes: Option<String>,
    pub mfa_secret: Option<SecretBuf>, // new field, optional
}
```
- MessagePack ignores unknown fields during deserialization
- Old clients skip new field, write it back unchanged

## Consequences

**Positive:**
- Type-safe operations (no runtime type errors)
- Compact storage (MessagePack efficiency)
- Clear upgrade path (enum variants + optional fields)
- Rich domain model (each entry type has appropriate fields)
- Impossible to store malformed data (serde validation)

**Negative:**
- **Adding entry types requires code changes** (can't be purely data-driven)
  - Mitigation: `Generic` entry type provides escape hatch
- **Enum size**: Largest variant determines memory footprint
  - Mitigation: Box large variants (e.g., `Certificate(Box<CertificateEntry>)`)
- **MessagePack unfamiliarity**: Less common than JSON
  - Mitigation: Export to JSON supported (`padlock export --format json`)

## Alternatives Considered

1. **Key-value pairs only (all entries are HashMap<String, String>)**
   - **Rejected**: No type safety, runtime errors, verbose field access

2. **JSON serialization**
   - **Rejected**: 2-3x larger files, slower parsing, no significant usability benefit

3. **Protobuf**
   - **Rejected**: Requires schema compilation, less flexible evolution, larger runtime

4. **CBOR (Concise Binary Object Representation)**
   - **Rejected**: Similar to MessagePack but less mature Rust ecosystem

5. **Single `Entry` struct with all possible fields (nullable)**
   - **Rejected**: Unclear semantics (which fields valid for which "type"?), memory waste

6. **Trait-based polymorphism (`Box<dyn EntryTrait>`)**
   - **Rejected**: Loses `Clone`/`Serialize` without object-safe workarounds, more complex
