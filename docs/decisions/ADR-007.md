# ADR-007: Audit Logging (JSON Lines, HMAC Chain, Always-On)

## Status
Accepted

## Context
Padlock requires tamper-evident audit logging for:
- Compliance (SOC2, HIPAA, PCI-DSS may require access logs)
- Security incident investigation (who accessed what, when)
- User awareness (detect unauthorized access)
- Forensics (reconstruct timeline after breach)

The audit log must:
- Be tamper-evident (detect modifications/deletions)
- Be always-on (cannot be disabled by attackers)
- Capture all security-relevant operations
- Have minimal performance impact
- Be parseable for automated analysis

## Decision
Implement an **always-on, append-only audit log** with HMAC chain integrity:

**Format:** JSON Lines (one JSON object per line)
**Location:** `~/.padlock/audit.log` (or `$XDG_DATA_HOME/padlock/audit.log`)
**Integrity:** HMAC-SHA256 chain (each entry HMACs previous entry's HMAC)
**Rotation:** Daily rotation with archival (`.log.2024-01-15.gz`)

**Log Entry Structure:**
```json
{
  "timestamp": "2024-01-15T14:32:01.123Z",
  "event_type": "vault_unlock",
  "actor": "user@hostname",
  "vault_id": "5f3e1a2b...",
  "success": true,
  "details": {
    "unlock_duration_ms": 1842,
    "entry_count": 47
  },
  "hmac": "a3f2e1d...previous_entry_hmac_chained"
}
```

**Logged Events:**
- `vault_unlock` / `vault_lock`
- `entry_read` / `entry_create` / `entry_update` / `entry_delete`
- `ssh_key_sign` (SSH agent signatures)
- `git_commit_sign`
- `passphrase_change`
- `export` / `import`
- `audit_verify` (integrity check runs)

**HMAC Chain:**
```
Entry 1: HMAC(key, entry_1_data || "init")
Entry 2: HMAC(key, entry_2_data || entry_1_hmac)
Entry 3: HMAC(key, entry_3_data || entry_2_hmac)
...
```
- HMAC key derived from vault KEK: `HKDF(KEK, "audit-log-integrity")`
- Tampering breaks chain → `padlock audit verify` detects
- Deletion of entries → gap in chain → detected

**Always-On Requirement:**
- No configuration option to disable logging
- Logging failure is non-fatal (doesn't block operations) but logged to stderr
- Log writes are best-effort (don't block critical path)

## Rationale

### Why JSON Lines
1. **Streamable**: Parse one line at a time (works with `tail -f`, `grep`, `jq`)
2. **Robust**: Truncated file doesn't corrupt previous entries
3. **Standard**: Wide tool support (jq, Elasticsearch, Splunk)
4. **Human-readable**: Can inspect with `cat` / `less`
5. **Efficient**: Append-only writes, no parsing old entries

### Why HMAC Chain
1. **Tamper detection**: Cannot modify entry without breaking chain
2. **Deletion detection**: Gaps in chain detected by verification
3. **Truncation detection**: Last HMAC in file must match computed chain
4. **Efficient**: O(1) append, O(n) verify (only on explicit verify command)
5. **Standards-based**: HMAC-SHA256 (RFC 2104)

### Why Always-On
1. **Security**: Attacker cannot disable logging before malicious activity
2. **Forensics**: Complete timeline available even if attack wasn't detected in real-time
3. **Compliance**: Many frameworks require "no audit log disable" control
4. **Simplicity**: No configuration complexity

### Performance Considerations
- Append-only writes: ~0.1ms per entry (non-blocking)
- Buffered I/O: Write in batches to reduce syscalls
- Async writes: Log in background thread (Tokio)
- Log rotation: Daily rotation prevents unbounded growth

### Privacy Considerations
**What's logged:**
- Event type, timestamp, success/failure
- Entry ID (UUID), not entry content
- Operation metadata (duration, count)

**What's NOT logged:**
- Passwords, SSH keys, API keys, TOTP secrets
- Entry names (could be sensitive: "Bank of America Password")
- Search queries

## Consequences

**Positive:**
- Strong tamper-evidence (HMAC chain)
- Forensic timeline for incident investigation
- Compliance-ready (SOC2, HIPAA, PCI-DSS)
- Standard format (JSON Lines) integrates with SIEMs
- Always-on prevents attacker evasion

**Negative:**
- **Performance overhead**: ~0.1ms per operation (acceptable for vault use case)
- **Disk usage**: ~100 KB/day for typical usage (rotation mitigates)
- **Privacy concern**: Audit log reveals access patterns (mitigated by not logging entry names)
- **Cannot disable**: Some users may object on principle (acceptable for security-first tool)

**Mitigation:**
- Rotation + compression (gzip) keeps disk usage minimal
- Document privacy model clearly in README
- Provide `padlock audit export --anonymize` to remove identifying info before sharing

## Alternatives Considered

1. **Syslog integration**
   - **Rejected**: External dependency, requires syslog daemon, less portable, harder to verify integrity

2. **SQLite audit database**
   - **Rejected**: More complex, harder to verify integrity (no append-only guarantee), overkill for logs

3. **No integrity (plain JSON Lines)**
   - **Rejected**: Trivial for attacker to modify logs

4. **Merkle tree integrity**
   - **Rejected**: More complex, requires rebuilding tree for verification, HMAC chain is simpler

5. **Opt-in logging**
   - **Rejected**: Defeats security purpose (attacker disables before malicious activity)

6. **Binary format (Protobuf, MessagePack)**
   - **Rejected**: Less human-readable, harder to inspect with standard tools, no significant benefit
