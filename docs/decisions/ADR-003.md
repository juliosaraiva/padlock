# ADR-003: Vault File Format (Binary with MessagePack)

## Status
Accepted

## Context
Padlock stores credentials in an encrypted vault file. The format must:
- Detect tampering (integrity protection)
- Support schema evolution (versioning)
- Be compact (minimize file size)
- Enable atomic writes (prevent corruption)
- Facilitate efficient parsing without loading entire file

## Decision
Use a **custom binary format** with the following structure:

```
┌───────────────────────────────────────────────────────┐
│ Magic Bytes (8 bytes): "PADLOCK\x00"                 │
├───────────────────────────────────────────────────────┤
│ Version (2 bytes): major.minor (0x00 0x01 = v0.1)    │
├───────────────────────────────────────────────────────┤
│ Flags (2 bytes): reserved for future use             │
├───────────────────────────────────────────────────────┤
│ HMAC-SHA256 (32 bytes): integrity tag over all below │
├───────────────────────────────────────────────────────┤
│ Encrypted KEK (48 bytes): XChaCha20-Poly1305         │
│   - Nonce: 24 bytes                                   │
│   - Ciphertext: 32 bytes (KEK)                        │
│   - Auth tag: 16 bytes (Poly1305 MAC)                 │
│   - AAD: header (magic + version + flags)             │
├───────────────────────────────────────────────────────┤
│ Entry Count (4 bytes): u32 big-endian                 │
├───────────────────────────────────────────────────────┤
│ Encrypted Entries (variable): MessagePack array       │
│   - Each entry: {id, type, created, modified, data}   │
│   - Encrypted with per-entry DEKs derived from KEK    │
│   - Serialized to MessagePack before encryption       │
└───────────────────────────────────────────────────────┘

Total header size: 96 bytes (fixed)
```

**Serialization:** MessagePack for entry data structures
**Encryption:** XChaCha20-Poly1305 (see ADR-001)
**Integrity:** HMAC-SHA256 over (version + flags + KEK + entries)

## Rationale

### Binary Format Benefits
1. **Tamper detection**: HMAC-SHA256 over all content ensures integrity
2. **Fast parsing**: Fixed-length header enables O(1) version/integrity checks
3. **Compact**: Binary encoding reduces file size vs. JSON (~30-40% smaller)
4. **Atomic writes**: Small file size enables safe write-rename pattern

### MessagePack for Entries
1. **Schema evolution**: Self-describing format supports adding fields
2. **Compact**: More efficient than JSON, comparable to protobuf
3. **Rich types**: Native support for bytes, maps, arrays, timestamps
4. **Rust ecosystem**: Excellent serde integration (`rmp-serde`)
5. **Human-debuggable**: Can inspect with `msgpack-tools` CLI

### HMAC-SHA256 Integrity
- Prevents tampering with vault file
- Computed over (version + flags + KEK blob + encrypted entries)
- HMAC key derived from PDK: `HKDF(PDK, "vault-integrity-key")`
- Verified before decryption (fail-closed security)

### Version Field Design
- **Major version** (1 byte): Breaking changes (e.g., new crypto algorithm)
- **Minor version** (1 byte): Backward-compatible additions (e.g., new entry type)
- Enables graceful upgrade path: v0.2 can read v0.1 files
- Prevents downgrade attacks: older versions reject newer major versions

## Consequences

**Positive:**
- Strong integrity guarantees (authenticated encryption + HMAC)
- Efficient storage and parsing
- Clear upgrade path for format evolution
- Self-contained file (no external metadata)

**Negative:**
- Custom format increases initial implementation complexity (acceptable for security/efficiency gains)
- Requires full file rewrite for any change (mitigated by atomic write pattern)
- Binary format not human-readable (mitigated by export/import commands)

**Mitigation:**
- Document format thoroughly in SYSTEM_DESIGN.md
- Provide diagnostic tools: `padlock vault verify`, `padlock vault inspect`
- Export to JSON for interoperability: `padlock export --format json`

## Alternatives Considered

1. **JSON with PGP/GPG encryption**
   - **Rejected**: Verbose (~2-3x larger), complex key management, external dependency, no atomic operations

2. **SQLite with SQLCipher**
   - **Rejected**: Overkill for key-value storage, 200+ KiB overhead for empty DB, complexity of SQL injection prevention, poor atomic guarantees

3. **Protobuf binary format**
   - **Rejected**: Requires compilation step, less flexible schema evolution, larger runtime footprint

4. **CBOR (Concise Binary Object Representation)**
   - **Rejected**: Similar to MessagePack but less mature Rust ecosystem, minimal size difference

5. **Plain JSON with XChaCha20-Poly1305**
   - **Rejected**: 30-40% larger files, slower parsing, no significant usability benefit
