# ADR-004: SSH Agent Protocol (RFC 4251 over Unix Socket)

## Status
Accepted

## Context
Padlock provides SSH key management with agent functionality, allowing Git/SSH clients to use keys without exposing private key material. The solution must:
- Integrate with existing SSH tooling (`ssh`, `git`, IDEs)
- Prevent private key exposure (keys never leave the vault)
- Support standard SSH operations (sign, list identities)
- Work across platforms (macOS, Linux, Windows)
- Enable secure Git commit signing

## Decision
Implement an **SSH agent daemon** conforming to RFC 4251 (SSH Agent Protocol) over a **Unix domain socket** (macOS/Linux) or named pipe (Windows).

**Protocol:** SSH Agent Protocol (RFC 4251, Section 4.4)
**Transport:** Unix domain socket at `$XDG_RUNTIME_DIR/padlock-agent.sock` (or `~/.padlock/agent.sock`)
**Daemon:** Long-running background process (`padlock agent start`)
**Lifecycle:** Systemd user unit (Linux) / launchd plist (macOS) / Windows Service (future)

**Supported Operations:**
1. `SSH_AGENTC_REQUEST_IDENTITIES` → List available SSH keys
2. `SSH_AGENTC_SIGN_REQUEST` → Sign data with specified key
3. `SSH_AGENTC_ADD_IDENTITY` → Add key to agent (decrypt from vault)
4. `SSH_AGENTC_REMOVE_IDENTITY` → Remove key from agent memory
5. `SSH_AGENTC_REMOVE_ALL_IDENTITIES` → Clear agent state

**Security Model:**
- Keys decrypted on-demand into agent memory (mlocked)
- Vault remains locked between operations
- Configurable timeout: auto-lock after N minutes of inactivity
- Process isolation: agent runs as separate daemon

## Rationale

### Why RFC 4251 SSH Agent Protocol
1. **Universal compatibility**: Works with all SSH clients (`ssh`, `git`, IDEs, deployment tools)
2. **Standard protocol**: No custom integration needed
3. **Battle-tested**: Used by OpenSSH, PuTTY, KeePassXC, 1Password
4. **Minimal attack surface**: Simple request/response protocol, no complex state machine

### Why Unix Domain Sockets
1. **OS-level access control**: File permissions restrict socket access
2. **No network exposure**: Cannot be accessed remotely
3. **Efficient IPC**: Lower overhead than TCP
4. **Standard SSH convention**: `SSH_AUTH_SOCK` environment variable

### Daemon Architecture
```
┌─────────────────────────────────────────────┐
│  SSH Client (ssh, git, IDE)                 │
│  $SSH_AUTH_SOCK = ~/.padlock/agent.sock     │
└────────────┬────────────────────────────────┘
             │ RFC 4251 messages
             v
┌─────────────────────────────────────────────┐
│  Padlock Agent Daemon (padlock agent start) │
│  - Unix socket listener                     │
│  - Request parser/dispatcher                │
│  - Key cache (mlocked memory)               │
└────────────┬────────────────────────────────┘
             │ Vault unlock (on-demand)
             v
┌─────────────────────────────────────────────┐
│  Padlock Vault (encrypted on disk)          │
│  - SSH keys stored as Entry::SSHKey         │
│  - Decrypted only for signing operations    │
└─────────────────────────────────────────────┘
```

### Git Commit Signing Integration
- Configure Git: `git config gpg.format ssh`
- Sign commits: `git commit -S` (uses agent for signing)
- Verify signatures: `git log --show-signature`
- See ADR-006 for signing key management

## Consequences

**Positive:**
- Zero-friction SSH usage (clients just work via `SSH_AUTH_SOCK`)
- Private keys never written to disk unencrypted
- Standard protocol eliminates vendor lock-in
- Enables Git commit signing without GPG complexity
- Agent caching improves UX (unlock once, use many times)

**Negative:**
- **Daemon complexity**: Must manage process lifecycle, socket cleanup, error recovery
- **Platform differences**: Unix sockets (POSIX) vs. named pipes (Windows)
- **Caching risk**: Keys in memory vulnerable to process memory dumping (mitigated by mlock + auto-lock timeout)

**Mitigation:**
- Use `systemd` (Linux) and `launchd` (macOS) for robust daemon management
- Implement `mlock` to prevent key data from swapping to disk
- Configurable auto-lock timeout (default: 15 minutes)
- Agent confirmation prompt for critical operations (optional setting)

## Alternatives Considered

1. **GPG Agent (gpg-agent)**
   - **Rejected**: Requires GPG key conversion, more complex protocol, heavier dependency footprint

2. **Custom HTTP API**
   - **Rejected**: No compatibility with existing SSH clients, requires browser extension or custom integrations

3. **FIDO2/Hardware Security Modules**
   - **Not rejected, future enhancement**: Padlock can delegate to HSMs in Phase 9 (platform integration)

4. **No agent, manual key export**
   - **Rejected**: User must export private keys to ~/.ssh/, defeating the purpose of encrypted storage

5. **Named Pipes only (Windows style)**
   - **Rejected**: Non-standard on Unix, worse access control, less efficient
