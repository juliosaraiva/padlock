# ADR-005: Domain-Driven Design Architecture (Core Library Pattern)

## Status
Accepted

## Context
Padlock requires a maintainable, testable, and reusable codebase that:
- Separates business logic from I/O and platform-specific code
- Enables comprehensive testing without external dependencies
- Supports multiple frontends (CLI today, GUI/TUI/web later)
- Maintains clear architectural boundaries
- Facilitates code reuse across different platforms

## Decision
Adopt a **Domain-Driven Design (DDD)** architecture with strict separation:

```
┌─────────────────────────────────────────────┐
│  Adapter Layer (padlock-cli)                │
│  - Command-line parsing (clap)              │
│  - Terminal I/O (stdout/stdin)              │
│  - Filesystem access (std::fs)              │
│  - Platform APIs (keychain, systemd)        │
│  - Implements core traits (StorageBackend)  │
└────────────┬────────────────────────────────┘
             │ depends on
             v
┌─────────────────────────────────────────────┐
│  Domain Layer (padlock-core)                │
│  - Pure business logic (NO I/O)             │
│  - Crypto operations                        │
│  - Vault management (state machine)         │
│  - Entry CRUD                               │
│  - SSH agent protocol                       │
│  - Trait definitions (boundaries)           │
└─────────────────────────────────────────────┘
```

**Key Principles:**
1. **padlock-core is pure domain logic**: No `std::fs`, no `println!`, no platform APIs
2. **Adapters implement traits**: `StorageBackend`, `PlatformKeyring`, `SyncTransport`
3. **Dependency inversion**: Core defines interfaces, CLI provides implementations
4. **Testability**: Core can be tested without mocks, CLI tests use in-memory adapters

## Rationale

### Why DDD for Padlock
1. **Complexity management**: Crypto, state machine, and protocol logic benefit from isolation
2. **Future frontends**: GUI, TUI, web app, mobile can reuse `padlock-core` without changes
3. **Testing**: Core business logic tested without file I/O, terminals, or OS dependencies
4. **Security focus**: Core lib is easier to audit (smaller, no I/O side effects)
5. **Reusability**: Core can be embedded in other Rust applications

### Trait Boundaries (Hexagonal Ports)

**`StorageBackend` trait** (filesystem abstraction):
```rust
pub trait StorageBackend {
    fn read(&self, path: &Path) -> Result<Vec<u8>>;
    fn write(&self, path: &Path, data: &[u8]) -> Result<()>;
    fn atomic_write(&self, path: &Path, data: &[u8]) -> Result<()>;
}
```
- Core works with any implementation
- CLI uses `std::fs` implementation
- Tests use `InMemoryStorage` implementation

**`PlatformKeyring` trait** (OS credential storage):
```rust
pub trait PlatformKeyring {
    fn store(&self, key: &str, value: SecretBuf) -> Result<()>;
    fn retrieve(&self, key: &str) -> Result<SecretBuf>;
}
```
- Core defines interface
- CLI provides macOS Keychain, Linux Secret Service, Windows DPAPI adapters
- Tests use `NoOpKeyring`

**`SyncTransport` trait** (future cross-device sync):
```rust
pub trait SyncTransport {
    fn send(&self, chunk: &EncryptedChunk) -> Result<ChunkId>;
    fn receive(&self, id: &ChunkId) -> Result<EncryptedChunk>;
}
```
- Core implements sync protocol
- Adapters provide file, WebDAV, S3, etc. implementations

### Module Structure

**padlock-core** (lib crate, no binary):
```
src/
├── lib.rs                 # Public API surface
├── crypto/                # Encryption, KDF, HMAC
├── vault/                 # Vault state machine
├── entries/               # Entry CRUD, search
├── ssh_agent/             # SSH protocol handler
├── signing/               # Git commit signing
├── sync/                  # Sync protocol (Phase 10)
├── audit/                 # Tamper-evident log
├── generate/              # Password/key generation
├── traits/                # Adapter boundaries
└── types/                 # Shared domain types (Entry, Secret, etc.)
```

**padlock-cli** (bin crate):
```
src/
├── main.rs                # Entry point, clap commands
├── commands/              # One module per command group
│   ├── init.rs            # padlock init
│   ├── add.rs             # padlock add
│   ├── get.rs             # padlock get
│   └── agent.rs           # padlock agent
├── adapters/              # Trait implementations
│   ├── fs_storage.rs      # StorageBackend via std::fs
│   ├── keyring.rs         # PlatformKeyring dispatch
│   └── terminal.rs        # User input/output
└── error.rs               # CLI error mapping
```

## Consequences

**Positive:**
- **Testability**: Core fully tested without I/O mocks (327+ tests, 95%+ coverage)
- **Reusability**: Core lib can be used by GUI, TUI, web server, mobile apps
- **Clarity**: Clear separation between "what to do" (core) and "how to do it" (adapters)
- **Security audits**: Core lib is ~80% of code but easier to audit (no I/O side channels)
- **Parallel development**: Core and CLI teams can work independently via stable traits

**Negative:**
- **Initial complexity**: More files/modules than monolithic architecture
- **Indirection**: Must pass trait implementations to core functions
- **Boilerplate**: Trait definitions + multiple implementations

**Mitigation:**
- Document trait contracts clearly in `docs/SYSTEM_DESIGN.md`
- Provide example implementations in `crates/padlock-test-utils`
- Use `impl Trait` syntax to reduce verbosity

## Alternatives Considered

1. **Monolithic binary (all logic in main.rs)**
   - **Rejected**: Hard to test, impossible to reuse, tight coupling to CLI

2. **Plugin architecture with dynamic loading**
   - **Rejected**: Overkill for current needs, security risk (loading untrusted code), complex error handling

3. **Microservices (daemon + client)**
   - **Rejected**: Unnecessary IPC overhead, complex deployment, overkill for single-user tool

4. **FFI-based library (C ABI)**
   - **Rejected**: Limits use of Rust idioms, error handling complexity, unnecessary until non-Rust frontends exist

5. **Workspace with shared domain types (no trait abstraction)**
   - **Rejected**: Loses testability benefits, hard boundaries prevent tight coupling
