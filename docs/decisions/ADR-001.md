# ADR-001: Encryption Algorithm Selection (XChaCha20-Poly1305)

## Status
Accepted

## Context
Padlock requires authenticated encryption with additional data (AEAD) for vault file encryption. The cipher must provide:
- Confidentiality and authenticity in a single operation
- Resistance to nonce reuse attacks
- Pure Rust implementation for WASM compatibility
- Well-audited, standards-based algorithm
- Reasonable performance on both desktop and mobile platforms

## Decision
Use **XChaCha20-Poly1305** from the RustCrypto `chacha20poly1305` crate for all vault encryption operations.

**Parameters:**
- Cipher: XChaCha20 (256-bit key, 192-bit nonce)
- MAC: Poly1305 (128-bit authentication tag)
- Mode: AEAD (Authenticated Encryption with Associated Data)

## Rationale

### Technical Advantages
1. **192-bit nonce prevents reuse**: XChaCha20's extended nonce space (2^192) allows safe random nonce generation without birthday-bound concerns
2. **Pure Rust**: No C dependencies, works in WASM, easier to audit
3. **Constant-time**: Resistant to timing attacks in software implementation
4. **Standards-based**: draft-irtf-cfrg-xchacha (IETF RFC track)
5. **Performance**: Competitive with AES-GCM on platforms without AES-NI

### Security Properties
- Proven security under standard AEAD assumptions
- 256-bit key provides post-quantum security margin
- Poly1305 MAC provides 128-bit authentication strength
- No weak keys or IV requirements

## Consequences

**Positive:**
- No nonce management complexity (can use random nonces safely)
- Cross-platform consistency (no hardware dependencies)
- Future-proof for WASM/embedded deployments
- Active maintenance by RustCrypto working group

**Negative:**
- Slower than AES-GCM on Intel/AMD with AES-NI (acceptable for vault use case)
- Less widely deployed than AES (mitigated by IETF standardization)

**Mitigation:**
- For high-throughput scenarios (future sync), we can revisit and potentially offer AES-GCM as an alternative cipher suite

## Alternatives Considered

1. **AES-256-GCM**
   - **Rejected**: Requires hardware support (AES-NI) for secure constant-time implementation; 96-bit nonce requires counter management; C dependencies in most implementations

2. **ChaCha20-Poly1305 (96-bit nonce)**
   - **Rejected**: 96-bit nonce requires careful counter/state management to avoid reuse; XChaCha20 is strictly better for our use case

3. **AES-256-GCM-SIV**
   - **Rejected**: Nonce-misuse resistant but slower; less mature Rust implementations; unnecessary complexity given XChaCha20's nonce space
