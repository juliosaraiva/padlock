# ADR-002: Key Derivation Function (Argon2id)

## Status
Accepted

## Context
Padlock derives encryption keys from user passphrases. The KDF must be:
- Resistant to GPU/ASIC brute-force attacks (memory-hard)
- Resistant to side-channel attacks
- Tunable to balance security and usability
- Standards-compliant
- Well-supported in Rust ecosystem

## Decision
Use **Argon2id** with the following parameters:

```rust
Argon2::new(
    Algorithm::Argon2id,
    Version::V0x13,
    Params::new(
        19456, // memory cost: 19 MiB (19 * 1024 KiB)
        2,     // time cost: 2 iterations
        4,     // parallelism: 4 lanes
        None   // output length determined by use (32 bytes for master key)
    )
)
```

**Derived Keys:**
- Passphrase Derived Key (PDK): 32 bytes → used to decrypt KEK
- See ADR-008 for full key hierarchy

## Rationale

### Why Argon2id
1. **RFC 9106**: Official IETF standard (May 2021)
2. **Password Hashing Competition winner** (2015)
3. **Hybrid approach**: Combines Argon2d (data-dependent) and Argon2i (data-independent) to resist both GPU and side-channel attacks
4. **Tunable security**: Can adjust memory/time/parallelism as hardware evolves

### Parameter Selection

**Memory Cost (19 MiB):**
- Derived from RFC 9106 recommendation: "at least 15 MiB" for password hashing
- 19456 KiB fits common desktop/mobile RAM constraints
- Too large to fit in GPU cache, forcing expensive memory access
- Roughly 1-2 second unlock time on modern hardware

**Time Cost (2 iterations):**
- RFC 9106 minimum recommendation
- Balances security with user experience (sub-2-second unlock)
- Can be increased in future versions if hardware improves

**Parallelism (4 lanes):**
- Matches common CPU core counts (4-8 cores on user devices)
- Allows efficient multi-core utilization
- Prevents trivial GPU parallelization

### Security Analysis
- **Resistance to brute force**: 19 MiB × 2 iterations = ~38 MiB-iterations per guess
- **GPU inefficiency**: Memory bandwidth requirements make GPUs ~10x less efficient than CPUs
- **ASIC resistance**: Custom hardware must implement full memory-hard algorithm
- **Side-channel resistance**: Argon2id's hybrid mode mitigates timing attacks

## Consequences

**Positive:**
- Industry-standard algorithm with strong cryptographic foundation
- Adjustable security without breaking compatibility (store params in vault header)
- Good balance between security and UX (~1-2s unlock on typical hardware)
- Future-proof: can increase parameters as hardware improves

**Negative:**
- **2-second unlock delay**: May feel slow compared to biometric unlock (acceptable for security-first tool)
- **Memory requirement**: 19 MiB may be challenging on extremely constrained devices (mitigated by parameter tunability)
- **Battery impact**: Memory-hard operations consume power on mobile devices

**Mitigation:**
- Allow advanced users to adjust params via config (with strong warnings)
- Future: Platform-specific KDF (e.g., Secure Enclave on macOS) as optional alternative (see Phase 9 roadmap)

## Alternatives Considered

1. **scrypt**
   - **Rejected**: Less memory-hard than Argon2; older design (2012); no official RFC standard

2. **PBKDF2-HMAC-SHA256**
   - **Rejected**: Not memory-hard; vulnerable to GPU attacks; legacy algorithm

3. **bcrypt**
   - **Rejected**: Limited memory-hardness (4 KiB); fixed cost parameters; designed for password storage, not key derivation

4. **Argon2d (data-dependent only)**
   - **Rejected**: Vulnerable to side-channel attacks (timing analysis)

5. **Argon2i (data-independent only)**
   - **Rejected**: Less resistant to GPU attacks than Argon2id; Argon2id is strictly better
